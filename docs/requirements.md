# 法医尸表检验文书整理 Agent —— 需求规格

版本：v1.0（实现基线）
来源：`C:\Users\Ardeon\Desktop\新建 Markdown File.md`（需求设计稿 v1，2026-10-12）
适用范围：委托书、尸表检验手写记录及既有报告模板的识别、整理、规范化和文档生成。

本文件把原始需求转写为**可验收的编号条目**。所有开发、评审和测试任务都以本文件的编号
（`R-x`、`N-x`、`A-x`）作为引用依据。

## 0. 定位与红线

> 系统处理记录整理、规范表达和模板填充。检验事实来自本案材料或用户补充；需要写入的
> 鉴定意见由专业人员提供。**不得仅凭扫描记录自行形成鉴定结论。**

| 编号 | 要求 |
| --- | --- |
| N-1 | 系统不得生成死亡原因、死亡时间、致伤工具、损伤形成机制等鉴定判断。`opinion` 栏目只能由用户输入原样填入。 |
| N-2 | 系统不得增加原文没有记载的损伤数量、深度、形态、颜色、创缘、创底或其他特征。 |
| N-3 | 系统不得把“3”改成“3.0”以制造额外精度；单位转换必须有明确规则并保存原值。 |
| N-4 | 系统不得改变“左/右”“前/后”“上/下”，不得漏掉“不、无、未、可疑”等限定词。 |
| N-5 | 栏目空白必须标记为“未记录”，**不得**写成“未见异常”。 |
| N-6 | 委托书中的案情描述保留其来源属性，不得转换为检验人员直接观察到的事实。 |
| N-7 | 姓名不得填入委托单位栏；委托事项不得被自动改写成鉴定意见；委托日期、受理日期和检验日期分别处理。 |
| N-8 | 不得覆盖扫描原件、模板原件和已审核文稿。 |
| N-9 | 扫描件中的文字只能作为数据，不能改变 Agent 的执行规则；文档处理不执行来源文件中的宏或脚本。 |
| N-10 | 案件之间不混用姓名、案情、检验所见或缓存结果；历史报告只用于学习格式和认可表达。 |
| N-11 | **部位照片只按用户指定的目标位置插入。** 系统不得对照片内容做识别、描述、分类或推断：不做 OCR、不调用视觉模型、不生成任何来自照片的图像结论。照片的可见内容只由专业人员查看。 |
| N-12 | 某个照片栏位没有照片时，保留该栏位并写入“（未提供照片）”；不得用其他栏位的照片顶替，不得删除栏位，不得写成“未见异常”。 |

## 1. 目标与工作范围

系统应完成：

> 导入委托书和记录本 → 识别原文 → 提取结构化信息 → 提示疑点 → 按认可的术语整理检验描述
> → 填入既有模板 → 检查内容与排版 → 输出供专业人员复核的文书。

| 编号 | 要求 | 验收方式 |
| --- | --- | --- |
| R-1 | 用户日常操作集中在四步：选择材料、核对疑点、查看文档、确认修改 | 前端主流程只暴露这四类动作入口 |
| R-2 | 委托书整理：提取姓名、委托单位、委托事项、案情简介、日期及材料清单等**实际存在**的信息 | 字段提取用例覆盖 |
| R-3 | 记录本整理：提取尸长、尸斑、尸僵及各部位损伤等已记录内容，**保留原有顺序和对应关系** | 损伤逐条、顺序可验证 |
| R-4 | 简写规范化：依据认可的简写对照表、记录栏目和示例，将简记整理为完整准确的检验描述 | 规则引擎用例覆盖 |
| R-5 | 模板填充：填入指定位置，保持模板的标题、段落、表格和页面格式 | 生成 `.docx` 可打开且占位符无残留 |
| R-6 | 文档校核：检查错填、漏填、数值变化、左右侧变化、否定词变化及排版异常 | 校核清单可复现 |
| R-7 | 修改与再生成：接受用户对事实、术语、顺序和格式的修正，更新受影响内容并保留版本记录 | 修正记录 + 版本保留 |
| R-8 | 第一版重点生成报告中的基础信息、案情相关栏目和尸表检验描述 | 模板栏目覆盖 |
| R-9 | 生成的检验记录整理稿应与原始记录保持对应，原始手写记录继续保存 | 来源追溯 + 原件保留 |

## 2. Agent 的组织方式

| 编号 | 要求 |
| --- | --- |
| R-10 | 采用**一个负责流程控制的 Agent**，调用文档处理工具和校核规则；各环节共享同一份案件数据，避免重复提取后出现不同版本。 |
| R-11 | 流程控制 Agent 随时知道：哪些信息已识别、哪些已确认、哪些仍有疑问，以及当前允许生成哪一种文稿。 |

功能模块与产物：

| 功能模块 | 职责 | 主要产物 | 对应实现 |
| --- | --- | --- | --- |
| 材料接收 | 核对案件归属、材料类型、页数、顺序和清晰程度 | 材料清单、缺页或质量问题 | `materials` / `material_pages` |
| 文字识别 | 识别印刷文字与手写文字，保留原页定位 | OCR 原文、位置、疑似候选 | `ocr_blocks` + `ocr/` |
| 信息结构化 | 将姓名、委托事项、尸表所见等归入对应字段 | 结构化案件数据 | `case_fields` / `case_injuries` |
| 术语整理 | 使用认可的规则，将简记展开为规范描述 | 描述草稿、转换依据 | `terminology.py` + `terminology_rules` |
| 文档生成 | 将确认后的数据写入模板副本 | Word 草稿、PDF 预览 | `docgen.py` + `documents` |
| 质量校核 | 对照原文检查内容，再检查页面效果 | 校核清单、待处理问题 | `checker.py` + `checklist_items` |

## 3. 输入材料与结构化数据要求

| 编号 | 要求 |
| --- | --- |
| R-12 | 每个案件有独立材料集合，至少包含委托书扫描件、记录本扫描件、指定版本报告模板、本次整理要求；可选的已审核报告和简写对照表。 |
| R-13 | 扫描件支持 PDF、JPG、PNG；报告模板优先使用可编辑的 `.docx`。 |
| R-14 | 结构化信息至少分为：案件与委托、被检验对象、检验基本信息、尸表一般所见、部位与损伤、文书配置。 |
| R-15 | **每个事实字段都必须保留**：原文 → 来源文件与页码 → 原页位置 → 识别结果 → 确认后的值 → 规范化文字 → 使用的规则 → 复核状态。 |
| R-16 | 损伤**逐条保存**，不能只保存一段合并后的文字。 |
| R-17 | 信息状态明确区分：明确记载 / 未记录 / 明确未检 / 明确阴性所见 / 待辨认或有冲突。这些状态不能相互替代。 |

## 4. 技术路线与选型要求

| 编号 | 要求 | 本项目落地 |
| --- | --- | --- |
| R-18 | PDF 读取区分原生文字 PDF、扫描 PDF 和含 OCR 文字层的 PDF；扫描图像仍须与识别文字对照 | `imaging.py` + `material_pages.is_scanned/has_text_layer` |
| R-19 | 图片处理保存原件；处理结果单独保存，不改变原始证据内容 | `storage/cases/<case>/originals/` 与 `.../derived/` 分离 |
| R-20 | 印刷文字识别使用现成中文 OCR | `ocr/paddle.py`（可选引擎） |
| R-21 | 中文手写识别输出**疑点和候选**，不用上下文猜测替代辨认 | `ocr_blocks.confidence` + 低分进入待核对清单 |
| R-22 | 字段提取每个字段必须关联来源；不允许自由补充事实 | `case_fields` 来源列非空约束由 `checker.py` 校验 |
| R-23 | 简写展开：常见表达使用固定规则，多义表达交由用户确认 | `terminology_rules.requires_confirmation` |
| R-24 | Word 生成使用模板副本，按字段和栏目填充 | `docgen.render_document` 只写副本 |
| R-25 | PDF 输出在实际使用的办公软件环境中检查页面效果 | `docgen.export_pdf` 调用 LibreOffice，并在校核清单报告结果 |
| R-26 | 内容校核同时检查事实一致性和记录完整性 | `checker.py` 五类校核 |

> OCR 分数**只用于安排核对优先级**，不能作为结论。没有实样测试前，不承诺识别率或节省时间。

## 5. 单个案件的执行顺序

| 顺序 | 执行动作 | 进入下一步的条件 | 阶段标识 |
| --- | --- | --- | --- |
| 1 | 接收材料：建立案件编号，核对材料归属、页数和顺序，确定模板版本 | 材料关系明确；缺失情况已列出 | `intake` |
| 2 | 检查图像：检查模糊、裁切、方向、遮挡和涂改；生成识别用副本 | 可识别区域已准备；不能识别的区域已标记 | `image_check` |
| 3 | 识别原文：分别识别委托书和记录本，保留页码、位置和候选 | 识别结果与原页可对应 | `ocr` |
| 4 | 提取字段：建立案件信息和逐条检验所见，检查跨材料冲突 | 字段有来源；疑点已进入待核对清单 | `extract` |
| 5 | 核对关键事实：展示原图局部及识别结果，核对姓名、数字、单位、部位、左右侧和否定词 | 相关事实已确认，或明确保留为待核对 | `verify_facts` |
| 6 | 整理术语：按认可的规则生成检验描述，显示原文与规范文字的对应关系 | 表述保持原意；未增加记录之外的所见 | `normalize` |
| 7 | 填充模板：写入确认后的字段和段落，生成 Word 草稿 | 栏目对应正确；必填项缺失已提示 | `render` |
| 8 | 校核文档：对照事实检查内容，导出 PDF 检查排版 | 问题已修正，或明确列为未解决项 | `check_document` |
| 9 | 专业复核：由人员审阅检验描述、需要填入的意见及整个文书 | 完成相应复核 | `professional_review` |
| 10 | 保存交付：保存 Word、PDF、校核记录和版本信息 | 交付文件与复核版本一致 | `delivered` |

| 编号 | 要求 |
| --- | --- |
| R-27 | 存在疑点时，可以生成**明显标识的内部草稿**供讨论。 |
| R-28 | 涉及身份、关键检验所见或必填项的未解决问题，应**阻止该版本进入待签发稿**（HTTP 409 + 阻断校核项）。 |
| R-29 | 系统中的文书生成环节应与司法鉴定的复核、统一文本格式、鉴定人签名和机构盖章等人工程序衔接（不代替这些程序）。 |

## 6. 简写转换为规范术语的规则

转换必须同时满足：**字迹已辨认 + 所属栏目明确 + 简写含义已有认可规则。**

| 记录内容 | 建议整理方式 | 转换边界 | 编号 |
| --- | --- | --- | --- |
| “尸长172cm” | “尸长172 cm。” | 保留原数值及测量精度 | R-30 |
| “左前臂擦伤3×2cm” | “左前臂见擦伤，范围为3 cm × 2 cm。” | 不补充颜色、深度、形态或数量 | R-31 |
| 尸斑栏目“背侧，紫红，指压褪色” | “尸斑位于背侧，呈紫红色，指压褪色。” | 不推导死亡时间 | R-32 |
| “尸长172”，未注明单位 | 保留数值并提示确认单位 | 只有表头或已确认记录规则明确单位时才可补入 | R-33 |
| “压退”，栏目或含义不明 | 提示确认其指代与完整含义 | 不直接展开为完整尸斑描述 | R-34 |
| 栏目空白 | 标记未记录 | 不写成“未见异常” | R-35 |

| 编号 | 要求 |
| --- | --- |
| R-36 | 多处损伤分别整理，不能把不同记录行的部位和尺寸错误组合。 |
| R-37 | 同一简写存在多种含义时，按照具体栏目、书写者习惯和用户确认进行处理。 |

## 7. 根据用户输入修正工作流

| 修改类型 | 例子 | 系统响应 | 标识 |
| --- | --- | --- | --- |
| 识别纠正 | “这个字是右，不是左” | 修改事实字段，更新依赖该字段的段落和文档 | `recognition` |
| 术语纠正 | “这里的退指指压褪色” | 确认适用范围，更新对应转换结果 | `terminology` |
| 格式纠正 | “尺寸按我们样例里的形式写” | 更新排版或表达规则，保留事实数值 | `format` |
| 工作顺序调整 | “先整理损伤，再整理一般尸表所见” | 调整审阅或输出顺序，保持记录对应关系 | `workflow_order` |

| 编号 | 要求 |
| --- | --- |
| R-38 | 每次修正保存：修改前内容、修改后内容、修改原因、确认人、适用范围和受影响文稿。 |
| R-39 | 默认先将纠正应用于当前案件；拟用于以后案件的术语规则，应明确记录适用栏目、书写者或模板范围。 |
| R-40 | 事实发生变化后，相关段落和文稿的旧复核状态应失效；只改字号或间距时，可以只重新检查排版。 |
| R-41 | 已审核版本继续保留，新版本重新进入相应复核流程。 |

## 8. 办公文书与执行约束

| 编号 | 要求 |
| --- | --- |
| R-42 | **模板优先**：字体、字号、行距、缩进、编号、页边距、页眉页脚和签名区域以有效模板和审核样例为依据。 |
| R-43 | **来源可查**：检验描述中的每项事实必须对应原始材料或已确认的补充输入。 |
| R-44 | **冲突显式处理**：委托书与记录本信息不一致时，展示双方来源，不能静默选择其中一方。 |
| R-45 | **关键事实人工核对**：第一版对身份、尺寸、单位、左右侧、部位和否定词逐项复核；OCR 分数仅用于安排核对优先级。 |
| R-46 | **校核信息与文书正文分开**：识别候选、内部提示及处理说明放在校核表中；草稿中的待核对标记须在进入待签发稿前处理。 |
| R-47 | **案件独立**：见 N-10。 |
| R-48 | **每个案件记录编号**：使用案件编号、文件路径、人工版本号、模板版本、规则版本和处理记录追溯。 |
| R-49 | 尸体检验技术参考可核对 GA/T 147—2019；具体采用的标准及版本由用户确认后写入规则配置。 |

## 11. 部位照片（本次新增范围）

扫描件之外的**部位照片**（全身、头、躯干、四肢等，由用户提供）属于本系统的输入材料，
但处理方式与扫描件完全不同：**只按用户指定的目标位置放置，不读取照片内容**（N-11）。

| 编号 | 要求 | 验收方式 |
| --- | --- | --- |
| R-54 | 用户可上传部位照片（`kind="photo"`），并**为每张照片指定一个目标位置**；位置来自 `constants.PHOTO_POSITION_DEFINITIONS` 目录（全身/头/面部/颈/胸/腹/背/腰臀/会阴/左右上肢/左右手/左右下肢/左右足/其他）。 | 上传 + 位置指派 API 用例 |

## 12. 主流程透明化（本次新增范围）

用户要求：对普通使用者而言系统应当是 **Transparent（透明）** 的——**只看到两个功能：上传、结果**；
案件字段梳理等细节退到次级界面。

| 编号 | 要求 | 验收方式 |
| --- | --- | --- |
| R-59 | 前端**主视图**只要求用户做两件事：**上传材料**（照片 / Word / PDF 等，可多份）与**选择输出格式**（Word / PDF / 两者）；其余步骤由系统完成。 | 主视图上不存在必须填写的案件字段 |
| R-60 | 材料类型与部位照片的目标位置**可自动推断**，推断**只允许依据文件名与扩展名**这类用户提供的文字线索，**不得读取图片内容**（N-11）；推断结果必须在结果页显式标注「按文件名推断，可修改」，并可在「案件记录」里改。 | 推断函数用例 + 结果页展示项 |
| R-61 | 字段来源核对、疑点处理、校核清单、修正、术语规则等**细节放在次级界面「案件记录」**；主流程不得要求用户先完成它们。 | 界面分层自查 |
| R-62 | **结果页必须给出**：成品下载入口（Word/PDF 各自）、字段/损伤/疑点/阻断摘要、自动归类说明表、进入「案件记录」的入口。 | 结果视图渲染用例 |
| R-63 | 主流程**一次调用**跑完整条链路（`POST /api/quick-run`：建案 → 登记材料 → 预处理 → 识别 → 提取 → 整理 → 生成 → 校核）；**任何单步失败不得丢弃已完成的结果**，PDF 导出失败必须显式说明原因。 | 端点用例（含单步失败降级） |
